# AIDEAL evaluation design review

The design is useful when it separates **environment readiness**, **executable API use**, and **task correctness**. These answer different questions. An LLM is optional for diagnosing a setup problem; it should not decide that an environment or experiment passed.

This review covers the code inspected on November 18, 2026. The currently authorized correction evaluates **Original and the existing D1 README at native R0**, with fresh programs, no repair feedback, and no D2 authoring. D1 has not been regenerated by the corrected author prompt. This review does not certify completed runs, readiness of every API, or paper-level task accuracy.

| Claim or question | Evidence needed | Current state and appropriate interpretation |
|---|---|---|
| The environment can execute this bank | Pinned source/runtime/fixtures; dependency and file checks; a known-correct program that passes and a deliberately incorrect program that fails for the expected reason; explicit coverage of special formats/tools | Deterministic runtime receipts and positive/negative launch gates exist. Missing prerequisites block relevant paid work. One control per library checks the execution mechanism, not all formats, optional tools, or APIs. Readiness remains scoped. |
| An agentic LLM is necessary to check setup | Evidence that fixed checks cannot resolve a concrete issue, followed by a validated repair proposal | No LLM is needed for ordinary import/build/file/hash/control checks. An optional diagnostic agent may inspect a failure and propose a pinned environment or fixture change. Deterministic rechecks must accept it before a new experiment; the agent's explanation cannot substitute for execution evidence. |
| Generated documentation improves executable API use | Same API bank, source, runtime, permitted input, audience model, limits and task prompt; separate recorded documentation exposure | The current fresh Original/D1 R0 comparison addresses this limited question. Audited historical requests have identical system/target context; SedonaDB differs only in output paths outside documentation. New neutral profiles/context apply symmetrically. Report **native acceptance**, not independently checked accuracy. |
| Generated documentation improves task correctness | A task and input/output contract fixed before generation, independent expected-output checks, and evidence that required APIs actually execute | Current native requests let the audience choose a small usage example and its own assertion. Exit status and an exact-target witness do not prove a nontrivial correct answer or actual target execution. A condition can change what the model chooses to test. The separate checker workflow requires execution, target reachability and oracle success, but this is not the current native R0 acceptance rule. |
| Aliases, hints and README changes have separate effects | Matched O, R, A, H, RA, RH, AH, RAH conditions; identical D1 wherever R=1; identical aliases/hints wherever enabled; validated builds and shared tasks | The paper describes the eight-condition factorial plan. The inspected condition-config code currently accepts five-arm, refactor-pair and six-arm designs, not the full eight-condition matrix. Current authorization covers O/R native R0 only. The eight-condition study remains planned. |
| Embedded hints improve repair | Frozen hints developed on development failures; guidance emitted through actual library diagnostics; matched H-on/H-off tasks; recorded delivered hints and R1/R2 outcomes | Native schema 3 routes emitted diagnostic text into repair feedback and forbids extra retrieved hint inputs. With no repair feedback at R0, hints should have no direct generation effect. Independent model draws can still yield different R0 percentages. Reexecuting the same initial program on both builds is a useful control for changed valid-call behavior. |
| Two repairs improve reliability | One initial attempt plus at most two code revisions on the same task; stop at success; retain failed programs, public feedback and each first-success round | The shared evaluation loop supports R0, R1 and R2. Current corrected launch sets repairs to zero. Report R0 and cumulative R2 separately; R2 includes prior R0/R1 successes. Provider retries are not code-repair rounds. A new no-feedback draw is not R1 repair. |
| Deep-dive README revision generalizes | D1 frozen for main ablation; D2 developed using development failures only; fresh evaluation with the same held-out tasks and repair policy; construction cost separated | The prepared D2 operator uses corrected R0 failures from the same API bank and tests authored examples. It labels this as development, not the planned post-R2 held-out study. D2 remains deferred. Success of the author's example is validation evidence, not a fresh audience result. |
| Learned error memory helps without contaminating comparisons | Record its initial contents, allowed retrieval, update timing and task split; reset or freeze it across independent trials/conditions; test memory separately if claiming its benefit | The shared controlled runner passes the current episode's previous program/feedback; it does not read global development notes. The older puzzle path defaults memory on and reads shared project notes/error logs. Do not import that default into held-out evaluation. Development memory can remain shared while evaluation memory is disabled or frozen and identical across arms. |
| Scores and efficiency support a scientific conclusion | Fixed scheduled denominators; unresolved setup/provider cases disclosed; per-library micro/puzzle results, uncertainty across repeated trials, and separated model/runtime/construction costs | Current native reports retain selected targets and distinguish prior, replay and fresh costs. They do not provide a six-library independently checked puzzle/factorial result. Report libraries separately so MDAnalysis's much larger bank does not dominate an unexplained pooled score. The code's `paper_fresh_R0_eligible` flag indicates absence of reused trials only; it does not establish measurement validity. |

## Minimal next measurement controls

1. **Complete the authorized diagnostic comparison first.** Preserve Original/D1 native R0 artifacts, classify setup/provider/program failures separately, and explain recoveries and regressions with matched examples. Do not fill independent-accuracy tables with native acceptance.
2. **Validate a small fixed task bank before expanding it.** For each library, use explicit inputs and expected behavior, a reviewed reference program and a plausible wrong program that the checker rejects. Include task-specific edges such as raster coordinate units, aspect-ratio preservation, or array-axis semantics. Validate required API use independently of the model's printed marker.
3. **Freeze development and evaluation boundaries.** Build D1, aliases and hints from development evidence. Keep them unchanged within the measured repair episode. Revise D1 to D2 separately, then start fresh audience trials. Record source access and public-feedback exposure explicitly.
4. **Add the planned conditions and repairs only after their gates work.** Use the same task bank, model/settings, runtime and prompt rules across the eight conditions. Keep both micro and puzzle results separate. Repeat matched trials and balance condition order when drawing reliability or efficiency conclusions.
5. **Treat optional agentic setup repair as preparation.** Record its prompts, actions, costs and environment changes separately. Rerun deterministic checks and freeze a new runtime profile. Never let setup diagnosis revise a hidden expected answer, a failed audience program, or the scoring rule during evaluation.
